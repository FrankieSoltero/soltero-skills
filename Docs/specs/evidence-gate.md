# Skill Spec — evidence-gate

- **Problem:** Agents claim "tests pass", "reviewed", "done" in natural language, and
  downstream steps — later agents, gates, and humans — act on those claims without any
  machine-checkable evidence. Worse, evidence generated against stale code silently passes:
  the tests ran, but not against the tree that is about to ship.
- **Trigger:** Whenever an agent is about to make, accept, or act on a
  **lifecycle-advancing claim** — a phase change, a review pass, a test certification,
  "done", "merge-ready" — either as the claimant (produce a receipt) or as the gatekeeper
  (demand and re-verify one).
- **Scope:** Produce and verify hash-bound, fail-closed JSON verification receipts under
  `Docs/evidence/receipts/`, using bundled deterministic scripts. Non-goals: gating
  ordinary developer notes, rationale, or docs (advisory-only, explicitly excluded);
  replacing CI; adjudicating *which* command constitutes adequate verification (that stays
  a human/reviewer decision — the skill guarantees the command's run is bound to the tree,
  not that the command was the right one).
- **Success scenario:** An agent finishes a feature and reports "all tests pass,
  merge-ready." A gatekeeper agent refuses the prose, requires a receipt; the claimant runs
  the bundled create script (which runs the test command, records exit code, digests the
  output, and hashes the tracked tree). The claimant then edits one more file "just a
  comment". At the gate, the bundled verify script re-hashes the live tree, detects the
  treeHash mismatch, and the gate FAILS — the claimant must re-run verification against
  the current tree before the lifecycle advances.
- **Bundled assets:** `scripts/create-receipt.mjs`, `scripts/verify-receipt.mjs`,
  `references/receipt-format.md` (the shared contract), `references/reference.md`
  (gatekeeper protocol details).

## Receipt format (SHARED CONTRACT — do not drift)

Receipts are JSON files under `Docs/evidence/receipts/`, one per verified claim. Fields:

| Field | Meaning |
|-------|---------|
| `claim` | The lifecycle claim this receipt certifies (string, e.g. "unit tests pass for feat/x") |
| `command` | Executable that was run |
| `args` | Array of arguments |
| `cwd` | Working directory the command ran in |
| `exitCode` | Integer exit code of the run |
| `outputDigest` | sha256 of the full combined output; the full output is stored alongside (or path-referenced) so the digest is re-checkable |
| `treeHash` | Hash of the tracked source tree at verification time, computed over `git ls-tree` of HEAD plus a digest of tracked-file worktree content, excluding the receipts dir itself |
| `timestamp` | ISO-8601 time of the run (informational; never a substitute for treeHash) |
| `producedBy` | Agent/session identifier of the producer |

Sibling skills (`memory-gardener` verified-by stamps, `skill-gardener` audit findings,
`skill-patcher` patch PRs — built in parallel, natural consumers of receipts) read this
exact format; changes to it are breaking changes and require coordination, not drift.

## Gate semantics (FAIL-CLOSED)

- Missing, malformed/incomplete, stale (treeHash no longer matches the live tree), or
  unauthorized evidence **blocks** the lifecycle transition. The default answer is NO.
- The agent's own natural-language report is **never** acceptable evidence for a gated
  claim — not from the claimant, not relayed by an orchestrator, regardless of confidence,
  seniority framing, or how plausible the prose is.
- A non-zero `exitCode` is a *valid receipt of a failed verification* — it blocks the gate
  but is kept: **a newer clean pass never masks a still-open earlier finding.** A blocking
  receipt (or recorded finding) stays blocking until it is explicitly resolved and
  re-verified against the current tree, not merely followed by a later green run.
- Advisory content (notes, rationale, design docs) is exempt: no receipts required, and
  the gate must not be extended to cover it. Restrict the heavy machinery to claims that
  actually move the lifecycle.

## Re-verification

A later gate re-verifies a receipt **offline and mechanically** with the bundled
`verify-receipt.mjs`: re-hash the live tracked tree and compare to `treeHash`, re-digest
the stored output and compare to `outputDigest`, check structural completeness. No LLM
judgment in the loop for these checks. Deterministic logic ships as bundled scripts in the
skill's resources rather than being regenerated by the agent each run (playbook **Proven**:
ship deterministic skill logic as bundled scripts — Warp + Anthropic skill-authoring docs,
via 2026-07-17 sweep).

## Cost honesty

Evidence gating is not free: expect roughly **~1.2x** token/time overhead versus a plain
retry loop, and up to **~3.8x** versus fully ungated operation. This spec states the
overhead rather than hiding it; the mitigation is scope discipline (gate only
lifecycle-moving claims), not pretending the receipts are free.

## Evidence basis (playbook tiers)

- **Promising** — default every lifecycle gate to fail-closed (Proof-or-Stop,
  arXiv 2607.14890).
- **Promising** — bind verdicts to a source-tree hash and never accept the agent's own
  "all tests passed" as evidence (arXiv 2607.14890).
- **Promising** — signed/self-contained JSON receipts a later gate can mechanically
  re-verify (arXiv 2607.14890).
- **Promising** — expect and openly report the gating overhead (arXiv 2607.14890).
- **Proven** — ship deterministic skill logic as bundled scripts (Warp + Anthropic
  skill-authoring docs, via 2026-07-17 sweep).
- **Promising** — restrict heavy evidence machinery to lifecycle-moving claims
  (2026-07-17 sweep).

## v1 simplifications (explicit)

Cryptographic signing of receipts (HMAC over the receipt body, key from the environment)
is specced as an **optional hardening level only — not implemented in v1**. v1's core is
hash-binding (treeHash) + content digests (outputDigest), which defeats staleness and
accidental drift but not a deliberate forger with write access to the receipts dir. When
HMAC hardening lands, `signature` and `keyId` fields extend the contract additively.

## Integration

`memory-gardener`, `skill-gardener`, and `skill-patcher` (parallel branches) consume
receipts: verified-by stamps, audit findings, and patch PRs respectively can each point at
a receipt path instead of restating prose claims. This spec references them by name only
and depends on none of their files.

## Testing

Repo `creating-a-skill` conventions: RED baseline then GREEN under
`tests/scenarios/evidence-gate/`. Scenarios must include:
(a) a stale-treeHash receipt correctly failing the gate;
(b) a prose-only "tests passed" claim correctly rejected;
(c) a valid receipt passing re-verification via the bundled script.
Gates: `node tools/lint-frontmatter.mjs`, `claude plugin validate ./ --strict` (where
available), `npm test`.
